## 第二部分：逐题参考答案

### Q1. 你先用 1 分钟介绍一下这个项目，解决了什么核心问题？
这个项目是一个面向软件开发流程的多 Agent 协作系统。核心目标是把需求分析、架构设计、编码、测试、评审这些阶段标准化编排起来。项目重点不是“让 Agent 自由聊天”，而是“让流程可控、可观测、可复用”。

具体解决了三类问题：
- 用有限状态机约束流程，解决多 Agent 自主协商导致的不可控。
- 用向量记忆复用历史任务经验，减少重复推理成本。
- 用端到端 Trace 定位瓶颈，把故障排查时间缩短到分钟级。

### Q2. 为什么要做多 Agent，而不是一个大 Prompt 的单 Agent？
单 Agent 在简单任务上可行，但在复杂软件任务上会同时承担多个角色，容易出现上下文混乱和目标漂移。多 Agent 的价值是“角色分离 + 责任边界清晰”。

例如 Architect 关注方案、Coder 关注实现、Tester 关注验证、Reviewer 关注质量。每个 Agent 的 prompt 和输出格式都可单独优化，整体可维护性和可调试性更好。

### Q3. 这个项目最有技术壁垒的点是什么？
我认为壁垒在“流程工程化”而不是“调用了多少模型 API”。真正难点是把开放式 LLM 行为收敛成稳定的生产流程，包括状态转移规则、异常回流、观测闭环、重试兜底、数据留痕。

换句话说，难的是系统设计与工程落地，而不是单点 prompt 技巧。

### Q4. 你在项目里最关键的个人贡献是什么？
关键贡献有三块：
- 设计并实现状态机驱动编排，把流程控制权从 Agent 决策收回到规则层。
- 落地向量记忆注入链路，完成“存储-检索-注入-验证”闭环。
- 建立 Trace 与指标采集，支持按状态查看耗时、token 和失败点。

### Q5. 这个系统上线后，怎么量化“真的有价值”？
我会看四类指标：
- 交付效率：端到端任务时长、中位数和 P95。
- 交付质量：一次通过率、回流次数、人工接管比例。
- 成本指标：单任务 token、单任务调用次数。
- 稳定性指标：任务成功率、超时率、异常恢复成功率。

如果这些指标在可比任务上持续改善，说明系统有实际价值。

### Q6. 为什么要用有限状态机替代 AutoGen 原生自由对话？
自由对话模式灵活，但难以保证每次都走同样路径，生产环境会出现不可复现和不可审计问题。状态机把流程显式化：
- 每一步该谁执行是确定的。
- 何时转移由 Guard 判定。
- 每次转移都有日志可追溯。

这使流程具备可预测性、可复盘性和可治理性。

### Q7. 你的状态集合是怎么设计的？每个状态的输入输出是什么？
状态设计遵循“一个状态只做一件事”的原则，通常包括需求分析、架构设计、编码、测试、评审、完成等。

每个状态都定义：
- 输入：上游产物 + 检索上下文 + 当前约束。
- 输出：结构化产物（设计稿、代码、测试结果、评审意见）。
- 退出条件：Guard 判定通过或失败。

### Q8. 状态转移表怎么定义？如何避免状态爆炸？
我会先定义主干路径（Happy Path），再补异常回流路径，形成有限转移矩阵。避免状态爆炸的方式：
- 把“动作参数”放到上下文，而不是新增状态。
- 把“是否通过”放到 Guard，而不是拆成大量中间状态。
- 把通用失败处理沉淀为统一错误状态或策略。

### Q9. Guard 函数具体判断什么，依据是什么？
Guard 主要判断当前产物是否满足下一状态进入条件。常见判断维度：
- 测试状态（通过/失败、失败数）。
- 评审状态（通过/需修改）。
- 结构化字段完整性（必填项是否齐全）。

理想做法是让 Agent 输出结构化 JSON，再由 Guard 解析字段，避免纯文本关键词误判。

### Q10. Guard 误判会导致什么后果？你如何降低误判率？
误判会导致两类风险：
- 假阳性：错误结果被放行，后续阶段成本更高。
- 假阴性：本可通过却被打回，造成无效回流。

降低误判率的做法：
- 强制结构化输出并做 JSON Schema 校验。
- 引入双重判定（规则 + 轻量模型复核）。
- 对关键转移加人工确认开关。

### Q11. 测试失败、评审拒绝时的回流路径怎么设计？
回流路径必须显式且最短。比如：
- 测试失败：`Testing -> Coding`，并附带失败日志与用例。
- 评审拒绝：`Review -> Architect` 或 `Review -> Coding`，取决于问题层级。

关键是回流要携带“可执行反馈”，否则只会重复失败。

### Q12. 同一个任务多次回流会不会死循环？如何收敛？
会有死循环风险。常用收敛策略：
- 限制最大回流次数（如 3 次）。
- 超限后升级到人工接管（HITL）。
- 每次回流要求新增差异说明，避免原地重试。
- 对重复错误触发策略切换（换模型、换提示模板、降级执行）。

### Q13. 如果某个 Agent 一直输出低质量结果，状态机怎么兜底？
可做多级兜底：
- 同模型重试（温度降低、补充约束）。
- 切换备用模型或备用 Prompt 模板。
- 切换执行策略（更小步任务拆分）。
- 超过阈值后人工接管。

状态机层面体现为失败计数与策略分支，而不是无限重试。

### Q14. 状态机和工作流引擎（如 Airflow/Temporal）相比有什么取舍？
状态机优势是简单直观、规则清晰，适合当前规模快速演进。Temporal 这类引擎在持久化、重放、分布式可靠性上更强，但引入成本和复杂度更高。

我的取舍是先用轻量状态机完成业务闭环，规模增长后逐步迁移到更强的工作流底座。

### Q15. 你为什么选择 ChromaDB？和 FAISS / Milvus 比怎么选型？
ChromaDB 上手快、嵌入式部署轻量，适合单机场景和快速迭代。FAISS 性能好但偏库级能力，Milvus 更适合大规模分布式。

当前项目优先研发效率和集成成本，所以先选 ChromaDB。若数据量和并发提升，再评估 Milvus。

### Q16. 你把哪些内容写入向量库？切片策略是什么？
我会写入高价值、可复用的信息：需求摘要、架构决策、关键代码片段、测试失败模式、评审结论。

切片策略通常是语义块切分，不按固定字数硬切。每块附带元数据：任务类型、语言、时间、质量评分、来源阶段，方便后续过滤。

### Q17. 新任务检索时，query 怎么构造？Top-K 怎么选？
query 不只用原始需求文本，还会拼接任务类型、技术栈和关键约束，形成更可检索的查询表达。

Top-K 一般从 3~8 起步，结合离线评估调参。K 太小会漏信息，太大容易引入噪声并抬高 token 成本。

### Q18. 如何处理“检索到了但不相关”的噪声上下文？
我会做三层过滤：
- 检索前过滤：按元数据先筛（语言、任务类型、时间窗口）。
- 检索后重排：结合关键词覆盖度和相似度做 rerank。
- 注入前压缩：只保留和当前子任务直接相关的证据片段。

### Q19. 向量记忆如何避免“旧经验污染新任务”？
核心是“相关性 + 时效性 + 质量门控”。
- 相关性：限定任务域和技术栈。
- 时效性：给旧数据衰减权重或 TTL。
- 质量门控：只保留通过评审/测试的历史内容。

避免把过时或错误经验注入新任务。

### Q20. 你怎么评估向量记忆是否真的提升了效果？
采用 A/B 对照：同类任务分别开启和关闭记忆注入，比较以下指标：
- 一次通过率。
- 平均回流次数。
- 总 token 成本。
- 端到端耗时。

如果质量提升且成本可控，说明记忆策略有效。

### Q21. 为什么不用微调（Fine-tuning）而采用检索增强？
微调适合稳定任务分布，但知识更新慢且训练成本高。当前业务变化快，RAG 的优势是可实时更新知识库、改动成本低、可解释性更强（能看到引用了哪些历史）。

所以先选检索增强，后续对高频稳定任务再考虑小规模微调。

### Q22. 你的 Trace 系统记录了哪些关键维度？
最少要有：任务 ID、状态名、状态进入/退出时间、耗时、模型调用次数、token 用量、工具调用结果、错误码与堆栈、重试次数。

这样既能看“业务流程”，也能看“技术细节”。

### Q23. 为什么要把 Prompt Token 和 Completion Token 分开统计？
两者代表不同优化方向：
- Prompt 高：说明上下文冗余或检索注入过多。
- Completion 高：说明输出约束不清或任务拆分过粗。

分开统计才能准确定位成本问题，不会只看到一个总数。

### Q24. 一次任务慢，你如何用可观测数据快速定位瓶颈？
排查顺序一般是：
1. 先看状态耗时分布，定位最慢状态。
2. 再看该状态内模型调用次数和单次时延。
3. 再看工具调用日志（测试执行、文件操作、网络请求）。
4. 最后看重试与回流是否异常放大。

通常几分钟内能定位是“模型慢”还是“流程绕路”。

### Q25. 除了耗时和 Token，你还会补哪些指标？
我会补：
- 状态成功率与异常率。
- 每类异常的占比和恢复成功率。
- 人工介入率与介入位置。
- 输出质量代理指标（评审通过率、测试通过率）。

这些指标更接近业务价值。

### Q26. 采集可观测数据会不会影响性能？怎么平衡？
会有开销，尤其是高频日志和全量 trace。平衡方式：
- 关键路径全量采集，非关键字段采样。
- 异步写入，避免阻塞主流程。
- 大字段（如完整 prompt）按需开关，默认只存摘要和哈希。

### Q27. 多用户并发任务时如何隔离上下文和 WebSocket 推送？
以 task_id 作为最小隔离单元：
- 状态上下文、内存检索、日志都按 task_id 命名空间隔离。
- WebSocket 订阅关系绑定 task_id，只向对应连接广播。
- 持久化层按任务分区，避免串写。

### Q28. LLM 接口限流或抖动时，重试和降级策略怎么做？
策略分三层：
- 短期：指数退避 + 抖动重试，识别可重试错误码。
- 中期：并发限流与队列削峰，避免雪崩。
- 长期：模型多活（主备模型切换）、超预算自动降级。

并且每次重试都要打点，防止“无声失败”。

### Q29. Code Executor 的安全边界怎么设计，如何防止危险执行？
核心原则是最小权限：
- 文件系统限制在工作目录白名单。
- 命令层做黑白名单与参数校验。
- 执行层设置超时、资源限制、网络隔离。
- 审计层记录执行命令、输入输出、退出码。

生产环境最好使用容器沙箱隔离。

### Q30. 你的系统如何保证可恢复（中断后续跑、断点恢复）？
关键是状态持久化和幂等设计：
- 每次状态完成后持久化快照（状态名、上下文、产物引用）。
- 恢复时从最后成功状态继续，不重复执行已完成步骤。
- 工具调用要设计幂等键，避免恢复后重复副作用。

### Q31. 你做了哪些自动化测试来保证状态机正确性？
测试分三层：
- 单元测试：Guard 判定、转移函数、异常分支。
- 集成测试：完整工作流在典型输入下的路径验证。
- 端到端测试：从 API 触发到 WebSocket 事件再到落库验证。

重点覆盖失败回流和超时重试这两类高风险路径。

### Q32. 线上出现“任务卡住不动”时，你的排障步骤是什么？
我会按“先外部后内部”排查：
1. 看任务是否还在队列或被限流阻塞。
2. 看当前状态是否在等待 HITL 事件。
3. 看最近一次模型调用和工具调用是否超时未返回。
4. 看状态机是否进入了无出口分支。
5. 必要时用任务快照强制恢复或人工终止。

### Q33. 如果把系统从串行改为部分并行，你会怎么改状态机？
我会引入“并行子状态 + 汇聚状态（join）”模型：
- 可并行的子任务各自执行并独立打点。
- 在 join 状态做结果聚合和一致性校验。
- 对共享上下文加版本控制，解决并发写冲突。

### Q34. 如果要支持“工具调用失败自动换工具”，你怎么设计？
设计一个工具策略层：
- 每个能力域注册主工具和备选工具。
- 工具失败按错误类型路由到不同 fallback。
- 记录工具成功率与延迟，动态调整优先级。

这样可以把“工具选择”从 prompt 层提升到策略层。

### Q35. 如何给不同类型任务动态选择不同 Agent 编排策略？
先做任务分类（如 CRUD、算法、重构、故障修复），然后映射到不同 workflow 模板。模板可配置：状态集合、Agent 组合、Guard 规则、通过阈值。

线上可加入策略学习，根据历史成功率自动调优模板选择。

### Q36. 如何做成本优化，让效果基本不变但 token 下降 30%？
可从四个方向做：
- 压缩上下文：检索结果摘要化、去重、限长。
- 减少回流：提高 Guard 精度和首轮输出约束。
- 分层模型：简单状态用便宜模型，关键状态用强模型。
- Prompt 模板治理：删除低价值指令与冗余示例。

一般组合策略最容易达到 20%~40% 的成本下降。

### Q37. 这个系统最大的技术债是什么？你计划怎么还？
最大技术债通常是“规则与策略散落在代码里，配置与版本管理不统一”。

还债方案：
- 把状态机、Guard、Prompt、工具策略配置化。
- 建立版本化与灰度机制，支持回滚。
- 引入离线回放评测，防止策略变更引发回归。

### Q38. 如果让你从零重做一版，架构上会改哪三件事？
我会优先改三点：
- 引入更强工作流引擎做持久化执行与可靠恢复。
- 建立统一策略中心（Prompt/Guard/Tool/Model）与实验平台。
- 完整建设评测体系，把“主观好坏”变成可量化指标闭环。

这样系统会更适合长期演进，而不只是 demo 级可用。
