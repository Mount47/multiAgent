# 大模型应用开发岗位面试问题文档

> 针对「多 Agent 软件开发协作系统」项目，覆盖项目本身、底层原理、工程实践三个维度。

---

## 一、项目本身

### 1. 介绍一下你的项目
**参考回答**：
基于 AutoGen 构建了一个多 Agent 协作框架，核心解决了三个工程问题：
1. 用有限状态机替代自由对话，解决流程不可控问题
2. 用 ChromaDB 做语义记忆，实现跨任务上下文复用
3. 构建 Trace 系统实现端到端可观测，支持逐步骤调试

---

### 2. 为什么选择有限状态机而不是让 Agent 自主协商？
**参考回答**：
AutoGen 的 GroupChat 允许 Agent 自己决定谁说话，但这在生产场景有三个问题：
- 流程不可预期，相同输入可能走不同路径
- 可能出现 Agent 互相推诿导致无限循环
- 无法审计，不知道为什么走了某条路径

有限状态机通过预定义转移规则和 Guard 函数，把「Agent 自主决策」变成「规则驱动执行」，流程完全可控可审计。

---

### 3. Guard 函数是如何判断测试通过/失败的？会不会误判？
**参考回答**：
目前是基于关键词匹配：检查 Tester 输出中是否包含 `PASS`/`FAIL`/`ERROR` 等字符串。

会误判 — 这是当前的局限性。更健壮的方案是让 Tester 输出结构化 JSON（如 `{"status": "passed", "failed_count": 0}`），Guard 函数解析 JSON 字段而非关键词，避免自然语言歧义。

---

### 4. Memory 模块是怎么工作的？检索到的内容怎么注入 Prompt？
**参考回答**：
1. **存储**：每个 Agent 输出后，按角色分类存入 ChromaDB（代码存 `code_snippets`，分析/设计存 `conversations`）
2. **检索**：新任务开始时，用任务描述作为 query，ChromaDB 做余弦相似度检索，返回 Top-K 相关历史
3. **注入**：将检索结果拼接到 system prompt 末尾，格式如：
   ```
   --- Relevant Historical Context ---
   [历史任务1的架构设计]
   [历史任务2的代码片段]
   ---
   ```
4. LLM 在生成时自然参考这些上下文

---

### 5. Human-in-the-loop 是怎么实现的？工作流如何暂停和恢复？
**参考回答**：
利用 Python asyncio 的 Event 机制：
1. 工作流到达检查点（如架构设计完成）时，调用 `request_approval()`
2. 内部创建 `asyncio.Event`，通过 WebSocket 推送 `approval_request` 消息给前端
3. 工作流协程挂起等待 `event.wait()`
4. 用户在前端点击「确认」或「请求修改」，WebSocket 收到 `approval_response` 消息
5. 调用 `event.set()` 恢复协程，继续执行
6. 若 5 分钟无响应，超时自动继续

---

### 6. Token 消耗是怎么统计的？
**参考回答**：
AutoGen 的 `TaskResult` 包含 `usage` 字段，记录了每次 LLM 调用的 token 数。在工作流的消息回调中拦截这个字段，按状态（requirements_analysis/coding 等）分别累加 prompt_tokens 和 completion_tokens，存入 MetricsCollector。前端 Trace 页面可以看到每个状态的 token 分布。

---

### 7. 项目有什么不足？如果继续做会怎么改进？
**参考回答**：
- **Guard 函数太脆弱**：关键词匹配容易误判，应改为结构化输出 + JSON 解析
- **没有 Prompt 日志**：目前无法回溯每次 Agent 的完整 Prompt，调试困难
- **Memory 没有过期机制**：历史越多检索越慢，需要加 TTL 或按相关性剪枝
- **Agent 错误没有降级策略**：某个 Agent 调用失败直接报错结束，应有重试和 fallback

---

## 二、大模型基础原理

### 8. 什么是 RAG？和 Fine-tuning 的区别是什么？
**参考回答**：
- **RAG（检索增强生成）**：不改变模型权重，在推理时动态检索外部知识注入 Prompt。优点：知识可实时更新，成本低；缺点：依赖检索质量，上下文长度有限
- **Fine-tuning**：用特定数据微调模型权重，让模型学会特定风格/知识。优点：效果好，推理时无额外检索开销；缺点：训练成本高，知识更新需重新训练

本项目用的是 RAG 思路 — 不改模型，通过检索历史上下文增强推理。

---

### 9. Embedding 是什么？ChromaDB 是怎么做语义检索的？
**参考回答**：
Embedding 是将文本映射到高维向量空间的表示，语义相近的文本向量距离更近。

ChromaDB 的检索过程：
1. 存储时：用 embedding 模型将文本转为向量，存入向量数据库
2. 检索时：将 query 也转为向量，计算与所有存储向量的余弦相似度
3. 返回相似度最高的 Top-K 条结果

余弦相似度 = 两向量夹角的余弦值，值越接近 1 表示越相似。

---

### 10. 什么是 Prompt Engineering？你在项目中是怎么设计 Prompt 的？
**参考回答**：
Prompt Engineering 是通过设计输入格式、指令和示例来引导 LLM 输出期望结果的技术。

本项目中每个 Agent 都有专属 system prompt，核心设计原则：
- **角色明确**：明确告知 Agent 身份和任务范围
- **输出格式约束**：要求 Tester 输出必须包含 PASS/FAIL 关键词，Reviewer 输出必须包含 APPROVED/REVISE
- **上下文注入**：将 Memory 检索结果和前序 Agent 输出作为 context 传入

---

### 11. Agent 和普通 LLM 调用有什么区别？
**参考回答**：
- **普通 LLM 调用**：单次 Prompt → Response，无状态，无记忆，无工具
- **Agent**：有感知（接收上下文）→ 有规划（决定用哪个工具）→ 有行动（调用工具）→ 有反馈（观察结果）的循环，可以多步推理和使用外部工具

本项目中每个 Agent 既能调用工具（执行代码、安装依赖），也能接收前序 Agent 的输出作为上下文。

---

### 12. 什么是 Function Calling？
**参考回答**：
Function Calling 是 OpenAI/Anthropic 等提供的能力，让 LLM 以结构化 JSON 格式「声明」它要调用哪个函数、传什么参数，由外部代码实际执行后再把结果返回给 LLM。

本质是：LLM 做决策（调什么），代码做执行（真正运行），形成 LLM ↔ 工具的协作循环。

本项目的 Tool System 就是基于这个机制，AutoGen 自动处理 Function Calling 的解析和分发。

## 三、工程与系统设计

### 13. 为什么用 FastAPI + WebSocket 而不是 HTTP 轮询？
**参考回答**：
Agent 工作流运行时间不确定（几十秒到几分钟），HTTP 轮询有两个问题：
- 高频轮询浪费服务器资源
- 低频轮询导致事件延迟

WebSocket 是全双工长连接，后端可以主动推送事件，实时性好且资源占用低。本项目中 Agent 每输出一条消息就通过 WebSocket 推给前端，实现实时流式展示。

---

### 14. 如果多个用户同时提交任务，系统怎么处理并发？
**参考回答**：
每个任务在独立的 asyncio 协程中运行，通过 `asyncio.create_task()` 并发执行，互不阻塞。

WebSocket Manager 用 task_id 做隔离，每个任务有独立的连接集合，事件只推送给对应任务的订阅者。

但当前存在的问题：LLM API 并发调用可能触发限速（Rate Limit），需要加任务队列和并发限制。

---

### 15. 项目的安全风险有哪些？你是如何处理的？
**参考回答**：
主要风险是 Code Execution — 让 LLM 生成代码并在服务器上执行，可能导致：
- **路径遍历**：读写系统敏感文件
- **命令注入**：执行恶意 shell 命令
- **资源耗尽**：无限循环消耗 CPU/内存

当前处理方式：
- 路径白名单过滤（只允许在 workspace 目录下操作）
- 危险命令关键词过滤（如 `rm -rf`、`sudo` 等）
- 执行超时限制
