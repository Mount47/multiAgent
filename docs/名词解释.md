
  为什么重要：
  这是把状态机和 AutoGen 团队连接起来的桥。

  ———

  10. FSM / Finite State Machine / 有限状态机

  是什么：
  FSM 是一种流程控制模型：系统在有限个状态之间按规则跳转。

  在这个项目里指什么：
  状态包括：

  - requirements_analysis
  - architecture_design
  - coding
  - testing
  - code_review
  - revision
  - approved

  为什么重要：
  因为它把开放式对话变成受控流程。
  模型负责产生内容，状态机负责决定流程。

  ———

  11. State（状态）

  是什么：
  状态是系统当前所处的执行阶段。

  在这个项目里指什么：
  比如系统现在在 testing，就意味着：

  - 当前负责说话的是 tester
  - 下一步只能走 testing 相关的 transition

  为什么重要：
  因为状态把“当前该做什么”这件事离散化了，系统才好控制。

  ———

  12. Transition（状态迁移）

  是什么：
  Transition 是从一个状态跳到另一个状态的规则。

  在这个项目里指什么：
  例如：

  - testing -> code_review
  - testing -> revision

  为什么重要：
  因为 workflow 不是一条死线，而是有分支的。

  ———

  13. Guard

  是什么：
  Guard 是状态迁移条件。
  它回答的问题是：“这条边现在能不能走？”

  在这个项目里指什么：
  例如：

  - tests_passed
  - tests_failed
  - review_approved
  - review_revision_needed

  为什么重要：
  因为同一个状态后面可能有不同分支。
  没有 guard，就没法根据测试结果决定是返工还是进入 review。

  ———

  14. Verdict

  是什么：
  Verdict 就是“判定结果 / 裁决结果”。

  在这个项目里指什么：
  tester / reviewer 的输出里最关键的那个结论字段，例如：

  - PASSED
  - FAILED
  - APPROVED
  - REVISE

  为什么重要：
  因为状态机不理解整段自然语言，它只需要一个离散结论来决定下一步。

  ———

  15. JSON Verdict

  是什么：
  用 JSON 结构表达 verdict，例如：

  {"verdict": "APPROVED"}

  在这个项目里指什么：
  Guard 会优先从 agent 输出里抽这个 JSON，再读取 verdict 字段。

  为什么重要：
  因为自然语言太模糊，JSON verdict 更适合程序消费。

  ———

  16. Keyword Matching（关键词匹配）

  是什么：
  通过查找文本里有没有某些关键字来判断含义。

  在这个项目里指什么：
  如果抽不到 JSON verdict，guard 就退回看：

  - "ALL TESTS PASSED"
  - "TEST FAILED"
  - "APPROVED"
  - "REVISE"

  为什么重要：
  这是 fallback 机制，提高鲁棒性。
  但它不如结构化输出稳定。

  ———

  17. Structured Output（结构化输出）

  是什么：
  让模型输出固定结构，而不是一大段自由文本。

  在这个项目里指什么：
  虽然没做到强 schema enforcement，但 JSON verdict 已经是结构化输出的雏形。

  为什么重要：
  因为结构化输出更容易被代码解析，更适合和状态机、工具系统对接。

  ———

  18. Termination Condition（终止条件）

  是什么：
  系统在什么情况下停止执行。

  在这个项目里指什么：
  主要有两类：

  - reviewer 输出 APPROVED
  - 消息轮次超过上限

  为什么重要：
  因为多 agent 系统很容易死循环。
  没有 termination，系统可能一直跑不完。

  ———

  19. max_rounds

  是什么：
  最大对话轮数限制。

  在这个项目里指什么：
  状态机里默认是 30。

  为什么重要：
  防止工作流无限循环。
  它是一个护栏，不是效果优化参数。

  ———

  20. max_revisions

  是什么：
  最大返工次数限制。

  在这个项目里指什么：
  默认是 3。

  为什么重要：
  防止 coder/tester/reviewer 在返工链路上来回打转。

  ———

  21. Tool Use / Tool Calling

  是什么：
  模型不只是生成文本，还可以调用外部函数或系统能力。

  在这个项目里指什么：
  工具包括：

  - 执行代码
  - 运行测试
  - 写文件
  - 读文件
  - 安装依赖
  - 搜 memory
  - 存 memory

  为什么重要：
  没有工具，agent 只能“说会做”；有工具，agent 才能“真的做”。

  ———

  22. Function Calling

  是什么：
  大模型输出不是普通文本，而是一个“我要调用哪个函数、传什么参数”的结构化请求。

  在这个项目里指什么：
  项目依赖模型支持 function calling，才能让 agent 调用工具。
  如果模型不支持，会降级成无工具模式。

  为什么重要：
  因为这让 agent 能稳定地和代码系统交互，而不是靠 prompt 猜测。

  ———

  23. FunctionTool

  是什么：
  把 Python 函数包装成模型可调用工具的适配层。

  在这个项目里指什么：
  例如 execute_code_tool、run_tests_tool 都是 FunctionTool(...) 包出来的。

  为什么重要：
  因为模型不能直接调用普通 Python 函数，需要一个 tool schema 和描述层。

  ———

  24. Tool Registry（工具注册表）

  是什么：
  一个统一维护“有哪些工具、谁能用”的地方。

  在这个项目里指什么：
  ROLE_TOOLS 就是角色到工具列表的映射。

  为什么重要：
  因为工具权限不能靠 prompt 口头约束，最好靠代码硬限制。

  ———

  25. Least Privilege（最小权限原则）

  是什么：
  一个模块只拿到完成任务所需的最少权限。

  在这个项目里指什么：
  例如 reviewer 没有文件写入和执行代码能力，coder 有。

  为什么重要：
  因为权限越大，风险越高；职责越模糊，越难调试。

  ———

  26. reflect_on_tool_use

  是什么：
  工具调用后，agent 会基于工具结果再做一轮思考和组织回答。

  在这个项目里指什么：
  coder/tester 上开启了这个参数。

  为什么重要：
  因为工具结果本身只是原始反馈，agent 需要基于它判断下一步怎么做。

  ———

  27. Sandbox / Sandboxed Execution

  是什么：
  受限制的执行环境，用来降低执行不可信代码的风险。

  在这个项目里指什么：
  当前实际上是“轻量受控执行”：

  - 在 workspace 下写临时文件
  - 用 subprocess 执行
  - 限制超时

  为什么重要：
  因为 agent 会生成代码并执行，如果完全不控制，风险很高。

  注意：
  当前不是严格意义上的生产级沙箱，没有 CPU/内存/网络级隔离。

  ———

  28. subprocess

  是什么：
  Python 启动外部进程的方式。

  在这个项目里指什么：
  执行 Python 代码、跑 pytest、安装依赖，都是通过 subprocess.run(...)。

  为什么重要：
  因为比 exec() 更接近真实运行环境，也更容易做超时控制。

  ———

  29. Workspace

  是什么：
  agent 可以操作的工作目录。

  在这个项目里指什么：
  生成代码、读写文件、测试运行都限定在 workspace_dir 下。

  为什么重要：
  因为这是一种基本隔离。
  不希望 agent 随便改项目根目录或系统其他文件。

  ———

  30. Path Traversal Protection（路径穿越防护）

  是什么：
  防止通过诸如 ../../ 这种路径跳出安全目录。

  在这个项目里指什么：
  写文件工具会校验 Path(filename).name == filename，不允许复杂路径。

  为什么重要：
  这是文件工具最基本的安全措施。

  ———

  31. Dependency Installer

  是什么：
  安装 Python 包的工具。

  在这个项目里指什么：
  install_dependency(package) 允许 agent 执行 pip install ...

  为什么重要：
  因为生成代码后可能依赖额外库。

  风险：
  安装依赖是高风险动作，所以项目做了基础字符过滤，但仍不算强安全。

  ———

  32. Memory

  是什么：
  Agent 系统里的“记忆”不是人脑记忆，而是可被存储和检索的历史上下文。

  在这个项目里指什么：
  历史任务中的：

  - 对话产物
  - 代码产物

  会被存进向量库，后续任务可以再检索出来。

  为什么重要：
  因为它让系统有“经验复用”能力，而不是每个任务都从零开始。

  ———

  33. Long-term Memory（长期记忆）

  是什么：
  跨任务、跨会话保留的信息。

  在这个项目里指什么：
  ChromaDB 里存下来的 conversation/code 记录。

  为什么重要：
  因为它能被新任务复用，区别于一次性上下文。

  ———

  34. Short-term Memory（短期记忆）

  是什么：
  当前任务执行过程中临时保留的信息。

  在这个项目里指什么：
  严格说这个项目没有单独设计一个显式 short-term memory 模块。
  当前更多依赖：

  - team 对话上下文
  - task_input
  - 当前事件流

  为什么重要：
  因为很多人会问“你们 memory 是长期还是短期”。
  这个项目重点其实是长期语义记忆，不是专门的短期状态管理系统。

  ———

  35. Vector Memory / 向量记忆

  是什么：
  把文本编码成向量，用语义相似度做检索的记忆方式。

  在这个项目里指什么：
  ChromaDB 存的是 conversation 和 code 的 embedding 检索索引。

  为什么重要：
  因为你要找的是“语义相似的历史经验”，不是精确关键词命中。

  ———

  36. Embedding

  是什么：
  把文本映射成一个高维向量，使语义相近的文本在向量空间里更接近。

  在这个项目里指什么：
  虽然代码里没显式手写 embedding 逻辑，但 ChromaDB 查询依赖的就是 embedding-based semantic search。

  为什么重要：
  因为没有 embedding，就做不了真正的语义相似检索。

  ———

  37. ChromaDB

  是什么：
  一个轻量级向量数据库。

  在这个项目里指什么：
  存储：

  - conversations
  - code_snippets

  并支持语义查询。

  为什么重要：
  因为项目需要的是一个本地可持久化、易接入、足够轻量的向量存储方案。

  ———

  38. Collection

  是什么：
  向量数据库中的数据集合，可以理解成不同的逻辑表/桶。

  在这个项目里指什么：
  当前有两个 collection：

  - conversations
  - code_snippets

  为什么重要：
  因为不同类型数据分开存，更方便：

  - 控制检索粒度
  - 格式化输出
  - 后续加 metadata filter

  ———

  39. RAG
  
  是什么：
  Retrieval-Augmented Generation，检索增强生成。
  先检索相关信息，再把它作为上下文喂给模型。

  在这个项目里指什么：
  新任务开始前，系统先用任务描述去搜 memory，再把结果拼进 prompt。

  为什么重要：
  因为模型本身不会记住你项目历史，RAG 是把外部知识临时塞回上下文的常见方式。

  ———

  40. Memory-Augmented Agent

  是什么：
  带记忆增强能力的 agent。

  在这个项目里指什么：
  architect/coder 理论上可以利用 memory，系统在 workflow 启动前也会自动注入历史上下文。

  为什么重要：
  因为这让 agent 的决策不只依赖当前任务，还能利用历史经验。

  ———

  41. top-k

  是什么：
  检索时只取最相似的前 k 条结果。

  在这个项目里指什么：
  例如预注入时取 n_results=2。

  为什么重要：
  因为召回太多会带来：

  - token 成本升高
  - 无关信息污染
  - prompt 变胖

  ———

  42. Metadata

  是什么：
  附加在文档上的结构化标签数据。

  在这个项目里指什么：
  如：

  - task_id
  - phase
  - filename

  为什么重要：
  因为以后可以按 metadata 过滤，比如：

  - 只搜 coding 阶段经验
  - 只搜某类文件
  - 只搜某个任务域

  ———

  43. Metadata Filter

  是什么：
  检索时按 metadata 约束结果范围。

  在这个项目里指什么：
  底层接口支持 where 参数，但业务主链路还没真正充分用上。

  为什么重要：
  因为纯语义检索容易召回半相关内容，metadata filter 可以提升精度。

  ———

  44. Length Truncation / 长度裁剪

  是什么：
  把过长文本截断，防止过度占用上下文。

  在这个项目里指什么：
  memory 注入前会裁短，工具观测输入输出也会裁短。

  为什么重要：
  因为 agent 系统里上下文膨胀是常见问题。

  ———

  45. Chunking / 切块

  是什么：
  把长文本拆成多个较小片段分别索引和检索。

  在这个项目里指什么：
  严格说当前没有正式 chunking，只做了粗粒度截断。

  为什么重要：
  因为正式的 RAG 系统一般要切块，否则检索粒度太粗。

  ———

  46. Trace

  是什么：
  一次任务执行的完整运行轨迹。

  在这个项目里指什么：
  记录：

  - 任务开始/结束
  - 每个状态的开始结束
  - 每个状态耗时
  - token 消耗
  - 工具调用链
  - 最终状态

  为什么重要：
  因为日志是散的，trace 是一条链。
  它更适合定位“这一单任务到底发生了什么”。

  ———

  47. Metrics

  是什么：
  聚合后的数值型观测指标。

  在这个项目里指什么：
  比如：

  - total workflows
  - completed/failed
  - avg duration
  - token totals
  - agent call counts

  为什么重要：
  因为 trace 适合看单次任务，metrics 适合看整体趋势。

  ———

  48. Observability（可观测性）

  是什么：
  通过外部信号推断系统内部状态的能力。

  在这个项目里指什么：
  不仅有日志，还能看：

  - 状态迁移
  - token 分布
  - 工具链路
  - 错误 traceback
  - metrics dashboard

  为什么重要：
  因为 agent 系统天生比普通后端更像黑盒，可观测性是调试前提。

  ———

  49. WorkflowTracer

  是什么：
  专门追踪 workflow 执行过程的 tracer。

  在这个项目里指什么：
  负责状态 enter/exit、记录 duration 和 token。

  为什么重要：
  因为 workflow 的瓶颈往往出现在某个阶段，而不是整个任务总耗时。

  ———

  50. Token

  是什么：
  模型处理文本时的基本计费/计算单位。

  在这个项目里指什么：
  项目统计了：

  - prompt tokens
  - completion tokens
  - total tokens

  为什么重要：
  因为 token 直接关系到：

  - 成本
  - latency
  - 上下文长度
  - 是否容易超预算

  ———

  51. Prompt Tokens

  是什么：
  输入给模型的 token 数。

  在这个项目里指什么：
  包括 system prompt、用户任务、memory 注入、历史消息、工具结果等。

  为什么重要：
  它高通常意味着上下文装载过多。

  ———

  52. Completion Tokens

  是什么：
  模型输出生成的 token 数。

  在这个项目里指什么：
  agent 说的话、工具调用前后的模型输出都可能贡献 completion token。

  为什么重要：
  它高通常意味着模型输出过长或行为不够收敛。

  ———

  53. Tool Observation

  是什么：
  对一次工具调用的输入、输出、耗时、结果做记录。

  在这个项目里指什么：
  每次工具调用都会生成一条 observation，最终进入 trace 和事件流。

  为什么重要：
  因为 agent 调错工具、工具报错、参数不对，这些都需要可追踪。

  ———

  54. Sanitization / 脱敏

  是什么：
  在记录日志/trace 时，把敏感字段替换掉。

  在这个项目里指什么：
  如：

  - api_key
  - token
  - authorization

  会被替换成 ***

  为什么重要：
  因为可观测性不能以泄露敏感信息为代价。

  ———

  55. Persistence / 持久化

  是什么：
  把运行数据存起来，而不是只放在内存里。

  在这个项目里指什么：
  任务和事件存到了 SQLite。

  为什么重要：
  因为任务历史和事件流需要可查询、可回看。

  ———

  56. SQLite

  是什么：
  一个轻量级嵌入式关系型数据库。

  在这个项目里指什么：
  用来存 tasks 和 task_events。

  为什么重要：
  因为项目是原型/本地系统，SQLite 成本低、够用。

  ———

  57. SQLAlchemy Async

  是什么：
  Python 的 ORM 和异步数据库访问方式。

  在这个项目里指什么：
  项目通过 async engine/session 访问 SQLite。

  为什么重要：
  因为 API 和任务服务本身是异步结构，数据库访问也要适配。

  ———

  58. Repository Pattern（仓储模式）

  是什么：
  把数据访问逻辑从业务逻辑里抽出来。

  在这个项目里指什么：
  TaskRepository 负责：

  - create task
  - update status
  - add event
  - list/get task

  为什么重要：
  因为这样 TaskService 不需要直接写 SQL 或 ORM 细节。

  ———

  59. TaskService

  是什么：
  任务执行和生命周期管理的应用服务层。

  在这个项目里指什么：
  它负责：

  - 创建任务
  - 启动 workflow
  - 注入 memory
  - 记录 trace
  - 更新状态
  - 发布 websocket 事件
  - 自动存 memory
  - 处理 HITL

  为什么重要：
  因为它是项目的真正主链路中枢。

  ———

  60. WebSocket

  是什么：
  服务端和前端之间保持长连接，实时推送消息的机制。

  在这个项目里指什么：
  前端能实时看到：

  - agent 输出
  - 状态变化
  - 审批请求
  - 任务完成/失败

  为什么重要：
  因为 agent workflow 不是一次性 HTTP 返回，更像流式执行过程。

  ———

  61. Event Stream

  是什么：
  按时间顺序输出系统事件的流。

  在这个项目里指什么：
  包括：

  - agent 发言
  - tool 调用结果
  - memory 注入提示
  - system error
  - hitl 事件

  为什么重要：
  因为这让你能“看着系统一步步跑”，非常利于调试和演示。

  ———

  62. HITL / Human-in-the-loop

  是什么：
  人在系统执行关键点介入审批或纠偏。

  在这个项目里指什么：
  目前在两个 checkpoint 停下来等用户确认：

  - architecture_design
  - code_review

  为什么重要：
  因为不是所有阶段都适合全自动。
  架构和最终评审，往往是最需要人工把关的点。

  ———

  63. Approval Checkpoint

  是什么：
  需要人工确认才能继续的 workflow 节点。

  在这个项目里指什么：
  就是上面那两个阶段。

  为什么重要：
  因为这是一种风险控制机制。

  ———

  64. Consistency（一致性）

  这个词面试里很容易被泛化，你要区分不同层次。

  ### 流程一致性

  每个任务都按同样状态机规则走。

  ### 角色一致性

  同一个状态总是由同一个角色负责。

  ### 权限一致性

  每个 agent 只拥有其角色允许的工具。

  ### 数据一致性

  任务状态、事件、trace、memory 之间是否同步、是否可靠。

  在这个项目里为什么重要：
  因为 agent 系统最怕“说一套做一套”：
  文档说有、代码没挂；状态变了、UI 没更新；DB 写了、读的还是内存。

  ———

  65. Degraded Mode（降级模式）

  是什么：
  系统某项能力不可用时，不是直接失败，而是退回一个能力更弱但还能运行的模式。

  在这个项目里指什么：
  如果模型不支持 function calling，就创建“无工具 agent”。

  为什么重要：
  因为模型能力不一致是现实问题。
  降级比直接崩更工程化。

  ———

  66. Provider Abstraction（模型供应商抽象）

  是什么：
  把不同模型服务商包在统一接口后面。

  在这个项目里指什么：
  支持：

  - Gemini
  - OpenAI
  - DeepSeek
  - Ollama

  但上层 agent 统一通过一个 client 工厂拿模型。

  为什么重要：
  因为你不希望业务逻辑跟具体厂商 API 强耦合。

  ———

  67. OpenAI-Compatible API

  是什么：
  接口格式兼容 OpenAI Chat Completion 的服务。

  在这个项目里指什么：
  DeepSeek、Ollama 等通过这种兼容接口接入，所以能复用同一种 client 抽象。

  为什么重要：
  因为这大幅降低了多模型接入成本。

  ———

  68. Temperature

  是什么：
  控制模型输出随机性的参数。

  在这个项目里指什么：
  配置里大多设成 0.3。

  为什么重要：
  因为 workflow 型任务希望输出稳定，不希望太发散。

  ———

  69. Timeout

  是什么：
  超过设定时间就终止某次执行。

  在这个项目里指什么：
  例如：

  - 代码执行 30s
  - 测试执行 60s
  - 模型请求 60s

  为什么重要：
  因为 agent 系统里超时是非常常见的失败模式。
  没有 timeout，就容易卡死。

  ———

  70. Retry

  是什么：
  失败后自动重试。

  在这个项目里指什么：
  模型请求有 max_retries=2。

  为什么重要：
  因为外部 API 会有瞬时故障，重试能提升稳定性。

  ———

  71. Revision

  是什么：
  返工阶段。

  在这个项目里指什么：
  测试失败或 review 要求修改后，重新回到 coder 处理。

  为什么重要：
  因为软件开发不是线性一次成功，revision 是真实流程的一部分。

  ———

  72. Approved

  是什么：
  workflow 终态，表示任务通过。

  在这个项目里指什么：
  reviewer 给出 APPROVED 后，状态机会进入 approved，工作流结束。

  为什么重要：
  因为 agent 项目必须有明确“完成”的定义，不然很容易无限讨论。

  ———

  73. Failure / Failed

  是什么：
  任务执行中发生异常或无法完成。

  在这个项目里指什么：
  如果 workflow 抛异常，任务状态会被标成 failed，并记录 traceback。

  为什么重要：
  因为失败不是坏事，无法定位失败才是坏事。

  ———

  74. Evaluation

  是什么：
  用指标或基准任务评估系统效果。

  在这个项目里指什么：
  严格来说，项目现在更强的是 observability，不是完整 evaluation framework。

  为什么重要：
  因为很多人把 metrics 当 evaluation，这其实不完全一样。

  ———

  75. Benchmark

  是什么：
  一组固定任务，用来比较系统效果。

  在这个项目里指什么：
  当前没有正式 benchmark 任务集。

  为什么重要：
  因为如果你想证明多 agent 或 memory 真的有效，最终要靠 benchmark，而不是只靠演示。

  2. 把这些名词按照项目主链路重新串起来，讲成一遍 “从用户发起任务到工作流结束” 的完整流程版

 短期记忆和长期记忆怎么区分和处理；chroma和sqlite的分工一样吗


• 不一样，而且这两个问题正好是面试里非常常见的拷打点。你要把它们讲成两
  层：

  1. 记忆按语义用途怎么分
  2. 存储按数据类型怎么分

  下面我分开讲。

  ———

  一、短期记忆和长期记忆怎么区分

  先给一个最稳的定义。

  ### 1. 短期记忆是什么

  短期记忆指的是：

  只在当前任务、当前会话、当前执行链路里有效的上下文状态。

  它通常包括：

  - 当前用户任务描述
  - 前几轮 agent 对话
  - 当前阶段的中间结果
  - 当前工具调用结果
  - 当前状态机处于哪个 state
  - 当前是否在等待审批
  - 当前 task 的 event stream

  它的特点是：

  - 生命周期短
  - 强依赖当前任务
  - 过期很快
  - 更强调“当前流程可继续”

  你可以把它理解成：

  “这一次任务跑到现在为止，系统脑子里正在装着的东西。”

  ———

  ### 2. 长期记忆是什么

  长期记忆指的是：

  跨任务、跨会话、可复用的历史经验或知识沉淀。

  在软件开发 agent 场景里，长期记忆通常包括：

  - 历史需求分析结论
  - 历史架构设计方案
  - 历史代码片段
  - 历史测试经验
  - 历史 review 结论
  - 某些可复用的风格或模式

  它的特点是：

  - 生命周期长
  - 和单次任务解绑
  - 面向未来检索复用
  - 更强调“经验复用”

  你可以把它理解成：

  “系统过去做过的事情里，哪些值得以后再拿出来参考。”

  ———

  ### 3. 本质区别是什么

  最核心的区别不是“存多久”，而是服务目标不同。

  短期记忆服务的是：

  - 当前任务继续跑下去
  - 当前 agent 能接上上一轮上下文
  - 当前 workflow 不丢状态

  长期记忆服务的是：

  - 下一个任务不要从零开始
  - 相似问题能复用过去经验
  - 系统具备跨任务学习感

  一句话概括：

  - 短期记忆是为当前执行 continuity 服务
  - 长期记忆是为未来任务 reuse 服务

  ———

  二、这个项目里短期记忆怎么处理

  这里要特别严谨，因为这个项目并没有显式做一个名为“short-term memory”的
  独立模块。

  ### 1. 当前项目的短期记忆，主要分散在几处

  #### 1. task_input

  在 src/api/task_service.py:166 里，任务开始时会构造 task_input：

  - 原始任务描述
  - memory 检索结果
  - 后续可能追加 HITL feedback

  这其实是当前 workflow 的核心输入上下文。

  #### 2. AutoGen team 的消息上下文

  team.run_stream(task=task_input) 之后，整个 group chat 内部会维护当前
  对话消息序列。
  这相当于当前任务的会话记忆。

  #### 3. TaskRecord.events

  每个 task 的事件流被缓存在 TaskRecord.events 里，见 src/api/
  task_service.py:53。

  这也是一种短期运行状态的外显记录。

  #### 4. 当前状态和当前 agent

  例如：

  - current_agent
  - state_prompt_tokens
  - state_completion_tokens
  - pending_checkpoint
  - pending_content

  这些都属于当前任务运行态，不是长期资产。

  ———

  ### 2. 当前项目短期记忆的特点

  它的实现方式更接近：

  - 会话上下文 + 运行态变量 + 事件流

  而不是一个专门的 ShortTermMemoryStore。

  这意味着：

  - 当前任务能跑通
  - 当前阶段上下文能衔接
  - 前端能看到过程

  但它也意味着：

  - 短期记忆没有独立抽象
  - 跨进程恢复能力弱
  - 不适合做复杂 session state 管理

  ———

  ### 3. 如果面试官问“你们短期记忆怎么设计的”

  最稳的回答不是硬说“我们有完整短期记忆模块”，而是：

  > 当前项目没有单独抽象一个 short-term memory service。短期记忆主要由
  > 当前 task input、AutoGen 对话上下文、任务事件流和 workflow 运行态共
  > 同承担，也就是更偏会话态和执行态管理；项目重点实现的是长期语义记
  > 忆，而不是复杂短期状态管理。

  这个说法很稳，不会被代码反杀。

  ———

  三、这个项目里长期记忆怎么处理

  ### 1. 长期记忆的载体是什么

  是 MemoryStore，实现见 src/memory/store.py:15。

  底层用 ChromaDB，分成两个 collection：

  - conversations
  - code_snippets

  ### 2. 长期记忆存什么

  系统会把 workflow agent 的输出自动写进去，见 src/api/
  task_service.py:273。

  规则是：

  - coder 输出存到 code_snippets
  - product_manager / architect / tester / reviewer 输出存到
    conversations

  而且会带 metadata，比如：

  - task_id
  - phase
  - filename

  ### 3. 长期记忆怎么用

  新任务开始前，系统会自动检索相关历史上下文，再注入到 prompt 里，见
  src/api/task_service.py:165。

  所以它是一个典型流程：

  - 历史任务产物沉淀到向量库
  - 新任务描述作为 query
  - 检索 top-k 相似项
  - 拼接进当前任务输入

  这就是长期记忆的使用方式。

  ———

  ### 4. 为什么长期记忆适合用向量库

  因为长期记忆要解决的问题不是：

  - “按主键查某条记录”

  而是：

  - “找语义上相似的历史经验”

  这种需求天然适合：

  - embedding
  - semantic search
  - top-k retrieval

  所以长期记忆更适合用 ChromaDB，而不是单纯 SQL 表。

  ———

  四、短期记忆和长期记忆，应该怎么分工

  你可以给面试官一个非常清晰的分工表述：

  ### 短期记忆负责什么

  - 当前任务输入
  - 当前对话上下文
  - 当前工具结果
  - 当前 workflow 状态
  - 当前审批状态
  - 当前 event stream

  核心目标：

  - 保证当前任务执行连续性

  ### 长期记忆负责什么

  - 历史任务经验沉淀
  - 相似任务上下文检索
  - 跨任务复用
  - 历史设计/代码片段参考

  核心目标：

  - 提升未来任务的起点

  一句话总结：

  短期记忆解决“这次任务怎么接着做”，长期记忆解决“下次任务能不能少走弯
  路”。

  ———

  五、Chroma 和 SQLite 的分工一样吗

  不一样，完全不是一类东西。

  你可以直接说：

  > SQLite 和 ChromaDB 在这个项目里承担的是两种完全不同的数据职责：
  > SQLite 管理结构化事务型数据，ChromaDB 管理面向语义检索的非结构化记
  > 忆数据。

  这是最标准的回答。

  ———

  ### 1. SQLite 是干什么的

  SQLite 在这个项目里主要做任务系统的业务数据持久化。

  它存的东西在 src/persistence/models.py 里能看出来，主要是：

  - tasks
  - task_events

  也就是：

  - 任务 id
  - 任务描述
  - provider
  - status
  - error
  - created_at / updated_at
  - 每条事件的 timestamp / source / content

  这些数据的特点是：

  - 结构固定
  - 字段清晰
  - 需要 CRUD
  - 需要按 task_id 精确查询
  - 需要按时间排序
  - 需要维护状态一致性

  这类数据天然适合关系型数据库。

  ———

  ### 2. ChromaDB 是干什么的

  ChromaDB 在这个项目里做的是语义记忆存储和检索。

  它存的是：

  - conversation 文本
  - code snippet 文本
  - 以及附带 metadata

  这些数据的特点是：

  - 核心值是非结构化文本
  - 检索目标不是精确匹配，而是语义相似
  - 不太关心复杂事务
  - 更关心 embedding 和 top-k retrieval

  这类数据天然适合向量数据库。

  ———

  ### 3. 两者的本质区别

  你可以从“查询方式”来讲，这是最容易让面试官点头的。

  #### SQLite 的查询方式

  是这种问题：

  - task_id = 某个值 的任务是什么
  - 某任务有哪些事件
  - 按创建时间倒序列出任务
  - 某任务当前 status 是什么

  也就是：

  - 精确匹配
  - 条件过滤
  - 排序
  - 事务更新

  #### ChromaDB 的查询方式

  是这种问题：

  - 和“实现一个计算器 API”语义最像的历史任务有哪些
  - 和当前代码需求最相近的历史代码片段有哪些

  也就是：

  - 相似度检索
  - top-k 搜索
  - embedding query

  所以两者根本不是“谁替代谁”的关系，而是：

  一个是 OLTP/结构化业务存储，一个是 semantic retrieval/非结构化记忆存
  储。

  ———

  ### 4. 为什么不能只用 SQLite

  理论上你可以把所有文本也存进 SQLite。
  但问题是：

  - SQLite 适合存文本
  - 不适合原生做高质量语义相似检索

  也就是说：

  - 可以存
  - 但“不好搜相似”

  所以如果你想实现 memory augmentation，就会很别扭。

  ———

  ### 5. 为什么不能只用 ChromaDB

  反过来也一样。

  ChromaDB 不适合承担：

  - 任务状态机主数据
  - status 更新
  - error 更新
  - 时间排序的任务列表
  - 审批状态管理
  - 事务一致性要求高的业务记录

  所以你不能把任务表、事件表全交给向量库来管。

  ———

  ### 6. 更直白一点怎么讲

  你可以用一句特别好懂的话：

  SQLite 回答“这条任务记录在哪里”，Chroma 回答“哪段历史经验和当前任务最
  像”。

  这句话非常适合面试。

  ———

  六、这个项目里两者是怎么协作的

  ### SQLite 管当前任务

  - 任务创建时写入 tasks
  - workflow 事件写入 task_events
  - 前端查询任务详情、任务历史，主要靠它

  ### Chroma 管历史经验

  - workflow 过程中把阶段输出沉淀成 memory
  - 新任务开始前做语义召回
  - agent 需要时也可以主动查 memory

  你可以把它说成：

  - SQLite 是 system of record
  - Chroma 是 system of retrieval

  不过这里有一个现实细节要注意：

  当前代码里，TaskService 读任务时仍然优先用内存 _tasks，所以 SQLite 还
  没完全做到严格的唯一真相源。这是实现上的不足，但不影响 SQLite 的角色
  定位。

  ———

  七、面试官如果追问：那短期记忆该不该也放 Chroma？

  标准答案是：通常不应该。

  原因：

  ### 1. 短期记忆强调时效和准确状态

  例如：

  - 当前正在哪个 state
  - 当前 tool 执行结果是什么
  - 当前用户刚给了什么 feedback

  这些不是“相似性检索”问题，而是“当前真相状态”问题。

  ### 2. 向量检索不适合做当前状态管理

  你不会想通过 semantic search 去查：

  - “我现在是不是在 testing”
  - “我现在等待审批了吗”

  这些必须是精确状态，不应该模糊匹配。

  所以短期记忆更适合：

  - 进程内运行态
  - session store
  - DB 表
  - conversation context

  而不是向量库。

  ———

  八、如果以后要把短期记忆也做得更完整，应该怎么做

  这也是很好的延伸题。

  你可以说，未来可以把短期记忆拆成一个专门的 session state：

  - 当前 task 的 structured working memory
  - 当前阶段输出摘要
  - 当前待处理 issue 列表
  - 当前文件树快照
  - 当前未解决 review comments
  - 当前 approval checkpoint 状态

  这种数据更适合：

  - SQLite / Redis / 进程内 state store
  - 而不是 Chroma

  这样系统会变成：

  - 短期记忆：精确状态管理
  - 长期记忆：语义经验复用

  这就是比较成熟的分层。

  ———

  九、一句话总结

  ### 短期记忆 vs 长期记忆

  - 短期记忆：服务当前任务连续执行，偏会话态和运行态
  - 长期记忆：服务跨任务经验复用，偏语义检索

  ### SQLite vs ChromaDB

  - SQLite：管结构化业务数据和任务状态
  - ChromaDB：管非结构化历史经验和语义检索

  最适合面试的压缩表达是：

  > 这个项目里，短期记忆主要体现在当前任务上下文、对话消息和 workflow
  > 运行态上，没有单独抽象成一个 short-term memory 模块；长期记忆则通过
  > ChromaDB 做 conversation/code 的语义沉淀与检索。SQLite 和 Chroma 分
  > 工完全不同，前者负责结构化任务与事件持久化，后者负责语义相似检索，
  > 两者分别解决“当前任务状态管理”和“跨任务经验复用”这两类不同问题。
