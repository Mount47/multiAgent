  二、Guard 函数实际判定示例

  第 4 步 Tester 输出（节选）：

  运行了 8 个测试用例，3 个失败：
  - test_password_hashing: AssertionError ...                                                   
  - test_invalid_email: KeyError 'email'                                                        
  - test_jwt_expiry: TimeoutError                                                               
                                                                                                
  ```json         
  {"verdict": "FAILED", "passed": 5, "failed": 3, "details": [...]}                             
                                                                                                
  ### Guard 求值过程（`transitions.py`）
                                                                                                
  引擎按 yaml 顺序遍历 `from=testing` 的两条边：                                                
  
  ```python                                                                                     
  # 先试 tests_passed
  verdict = _extract_json_verdict(content)                                                      
  # → {"verdict":"FAILED",...}
  v = "FAILED"                                                                                  
  v in ("PASSED","ALL_TESTS_PASSED",...)  # False → 返回 False，跳过                            
                                                                                                
  # 再试 tests_failed                                                                           
  v in ("FAILED","TESTS_FAILED",...)  # True → 返回 True                                        
  → 进入 revision 状态，_revision_count=1。                                                     
                                                                                                
  第 7 步 Reviewer 输出                                                                         
                                                                                                
  {"verdict":"APPROVED","comments":"代码符合规范，加密强度足够"}
  → review_approved guard 命中 → 进入终态 approved。                                            
                                                                                                
  兜底机制                                                                                      
                                                                                                
  - 若第 4、5 步反复失败到 _revision_count > 3 → 强制进入 approved                              
  - 若总轮次 > 30 → 同样强制收口                                                                
  - 若 LLM 没输出 JSON 也没 keyword → 默认                                                      
  tests_passed=False、review_approved=False，倾向走更保守的修订分支

  每个 agent 完成后，_auto_save_to_memory() 落库一次。本任务共产生 6

  落库决策逻辑（量化）                                                                          
                                                                                                
  - 哪些存：白名单 _CONV_AGENTS = {pm, architect, tester, reviewer} →                           
  conversations；_CODE_AGENTS = {coder} → code_snippets                                         
  - 哪些不存：system 消息、HITL 暂停的中间态、tool_call 原始 trace                              
  - 截断：每条 ≤ 2000 char（≈500 token），避免单条噪声主导召回                                  
  - embedding：ChromaDB 默认用 all-MiniLM-L6-v2（384 维），成本约 0
  - 存储成本：6 条 × 2KB ≈ 12KB；vector 6 × 384 × 4B ≈ 9KB；忽略不计

  - 按当前 state 过滤：coding 阶段只查 code_snippets
  - 按 metadata.phase 过滤同一阶段的记忆，命中率更高

    → total_prompt_tokens=30080, total_completion_tokens=8150,
      total_tokens=38230, state_count=7, duration_ms=89100                                      
                                                                                                
  可派生的分析指标（这是 Trace 相对日志的核心价值）                                             
                                                                                                
  # 1. 哪个状态最贵？                                                                           
  sorted([(t.from_state, t.total_tokens) for t in trace.transitions], key=-1)                   
  # → [("code_review", 9050), ("testing#2", 8100), ("revision", 7300)...]                       
  # 结论：评审/测试阶段累积 context 最长，是优化重点                                            
                                                                                                
  # 2. prompt vs completion 比例                                                                
  prompt_ratio = trace.total_prompt_tokens / trace.total_tokens   # = 30080/38230 = 78.7%       
  # 结论：上下文占比过高 → 应优化历史拼接策略，而非压缩输出                                     
                                                                                                
  # 3. 工具调用失败率                                                                           
  failed = [t for t in trace.tool_calls if not t.success]                                       
  fail_rate = len(failed) / len(trace.tool_calls)                 # = 1/4 = 25%
  # 结论：run_pytest 一次失败一次成功，符合"修订循环"预期                                       
                                                                                                
  # 4. 状态平均耗时                                                                             
  [(t.from_state, t.duration_ms) for t in trace.transitions]                                    
  # → coding=22100ms 最慢；testing 平均 10.5s；架构设计 12.5s                                   
                                                                                                
  # 5. Token 成本（按 Claude Sonnet 定价 $3/M input, $15/M output）                             
  cost = 30080 * 3e-6 + 8150 * 15e-6 = $0.090 + $0.122 = $0.212                                 
  # 单任务成本可见 → 接入计费/预算告警                                                          
                                                                                                
  同等需求若用日志做（对比）                                                                    
                                                                                                
  要算"哪个状态最贵"得 grep + 正则 + awk + 跨行关联 task_id，且 token 数往往只 log 总数（无     
  prompt/completion 分离），更别提关联 tool_call 和 state——而 Trace 是对象树，一行 list 
  comprehension 就出结果。
