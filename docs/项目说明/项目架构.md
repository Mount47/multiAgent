一、项目定位

  这是一个多 Agent 协作软件开发系统：5 个专业角色（产品经理 → 架构师 → 程序员 →
  测试 → 评审）在有限状态机（FSM）驱动下，把一句自然语言需求自动跑成「需求分析 →
  架构设计 → 写代码 → 单测 → 代码评审」的完整流程，并带 Web 可视化。

  底座是 Microsoft AutoGen 0.4 的 SelectorGroupChat。从 docs/ 目录（面试问答.md、
  名词解释.md、single-agent-vs-multi-agent.md、benchmark.md…）和 PROJECT_STATUS.md
  里「重点从功能可用转向简历可信度和演示完整度」可以判断：这是一个面向面试/作品集
  的学习型工程，但完成度相当高（114 个测试通过，前后端闭环）。

  二、整体架构（分层）

  入口层    CLI (agent-dev)  │  FastAPI+WebSocket :8000  │  React+Vite UI :5173
  ─────────────────────────────────────────────────────────────────────
  编排层    SelectorGroupChat  ←(selector_func)→  WorkflowStateMachine(7状态)
  ─────────────────────────────────────────────────────────────────────
  能力层  Agents(5角色) │ Tools(7工具) │ Memory(ChromaDB) │ Models(4provider) │
  Observability
  ─────────────────────────────────────────────────────────────────────
  支撑层    Persistence(SQLite/SQLAlchemy async)  │  Config(YAML+Pydantic)

  代码组织清晰，src/ 13 个子模块、约 3400 行 Python；web/src/ 约 1500 行
  TS/TSX，组件按 workflow / metrics / trace / hitl / tasks / output 等领域拆分。

  三、核心机制（最关键的设计）

  用确定性状态机替换 AutoGen 默认的「LLM 选下一个发言人」。

  AutoGen 的 SelectorGroupChat 原本靠一个 LLM
  来决定下一个该谁说话。本项目把这件事接管为一个
  selector_func（orchestration/selector.py），内部驱动自定义 FSM：

  1. 状态定义（states.py）：7 个状态，每个状态映射一个 agent 角色。
  2. 转移表（config/workflows.yaml）：声明式定义 from → to + guard，加载到
  state_machine.py。
  3. Guard 
  函数（transitions.py）：每次拿最新一条消息判断是否转移。判定优先解析结构化 JSON 
  裁决（{"verdict":"APPROVED"}），失败则回退到关键字匹配——既稳又有容错。
  4. 安全边界：max_rounds=30、max_revisions=3，超限强制进入 APPROVED 终态，防止
  LLM 把流程跑成死循环。

  工作流：
  requirements_analysis(PM) → architecture_design(Architect) → coding(Coder)
     → testing(Tester) ──tests_passed──→ code_review(Reviewer) ──approved──→ ✅
          ↑                  └─tests_failed─→ revision(Coder)─┐
          └───────────────── revision ←── review_revision_needed ┘

  亮点：把「不可控的 LLM 路由」变成「可控、可测、可配置的 FSM」，这是 single-agent
  做不到、也是这个项目区别于普通 AutoGen demo 的核心价值。

  四、各模块功能

  模块: Agents (agents/)
  实现要点: 工厂模式按角色建 AssistantAgent；prompt 存为
    Markdown（config/prompts/*.md）；Coder 开
    reflect_on_tool_use=True；降级模式：模型不支持 function_calling 时自动建无工具

    agent 并改 prompt 让它直接写代码块
  ────────────────────────────────────────
  模块: Tools (tools/)
  实现要点: 7 个工具，按角色分配权限（registry）：Coder
    拿全套读写/执行/装依赖/记忆，Tester 只拿执行+跑测，PM/Reviewer
  无工具。同步实现
     + asyncio.to_thread 包成 async + @observe_tool_call 装饰器
  ────────────────────────────────────────
  模块: Memory (memory/)
  实现要点: ChromaDB 向量库，两个 collection（conversations /
    code_snippets），cosine 检索。RAG  闭环：任务开始前检索历史相关上下文注入
    prompt，agent 输出按角色自动回存
  ────────────────────────────────────────
  模块: Models (models/)
  实现要点: 4 个 provider（Gemini/OpenAI/DeepSeek/Ollama）统一走 OpenAI 兼容
    API，工厂按 provider 名缓存 client，支持每角色指定模型或回退 DEFAULT_MODEL
  ────────────────────────────────────────
  模块: Observability
  实现要点: WorkflowTracer（状态时长 + prompt/completion token 拆分 +
    工具调用链）、MetricsCollector（聚合指标）、tool_observer（ContextVar
    绑定回调，输入脱敏+截断+traceback）
  ────────────────────────────────────────
  模块: Persistence
  实现要点: SQLAlchemy async + aiosqlite，Task / TaskEvent 两表，内存缓存为读、DB
    为准
  ────────────────────────────────────────
  模块: API/Web
  实现要点: FastAPI 路由化（tasks/providers/workflow/workspace）+ WebSocket
    实时事件流；React UI 三栏：工作流图/指标/Trace + 事件流/代码 + HITL 审批弹窗
  ────────────────────────────────────────
  模块: Health
  实现要点: CLI/API 启动前预检：workspace 可写、python/pip/pytest 在位、API
    key、可选 LLM 连通性 ping

  五、端到端数据流

  POST /api/tasks → TaskService.create_task 落库并 asyncio.create_task 异步跑 →
  build_team() 组装带 FSM selector 的 SelectorGroupChat → team.run_stream()
  逐事件流出 → 每个事件：抽 token、追踪状态切换、写 TaskEvent、自动存 Memory、经
  WebSocket 推前端 → 工具调用经 ContextVar 回调写入 Trace → 完成后落
  metrics。前端用 WebSocket 实时高亮状态图、滚动事件流。

  六、我从代码里发现的几处实情（文档没明说的）

  1. HITL 的「revise」目前是半成品。task_service.py:239-240
  自己注释承认：用户点「revise」后只是把反馈 append 到 task_input，并没有真正重启
  team.run_stream——对已在运行的 stream
  不生效。「暂停等审批」是真的可用，「带反馈重跑」还没接上。
  2. 代码执行沙箱很弱。code_executor 和 dependency_installer 直接 subprocess
  在宿主机跑 agent 生成的任意 Python 和 pip install。README
  说的「安全」只是防路径穿越/命令注入字符，没有真正隔离。pyproject.toml 声明了
  autogen-ext[...,docker]，说明原本想用 Docker 执行，但落地的是 subprocess
  版。这是演示项目可接受、生产不可接受的点。
  3. 每条事件开一个新 DB session（_append_event / _set_status 每次 get_db() 再
  close）——量大时 DB 往返偏重，demo 无碍。
  4. 文档滞后于代码：PROJECT_STATUS.md 说 Memory「自动阶段存储未做（85%）」，但
  _auto_save_to_memory / _retrieve_memory_context 在 task_service
  里其实已经实现了。
  5. 状态表示有冗余：FSM 的 STATE_AGENT_MAP、task_service 的反向
  _AGENT_STATE_MAP、HITL_CHECKPOINTS 多处各维护一份映射；Tracer 的 to_states
  用「下一次 enter 时回填」的方式，最后一个 transition 的 to_state
  不会被填。都属小问题。

  七、总体评价

  设计上最值得称道的是**「FSM 接管 LLM
  路由」这一核心抽象**，以及围绕它做的配置化（YAML）、可观测性（trace/metrics/tool
  -chain）、降级容错（无工具模式、JSON+关键字双重 guard、轮次上限）。工程完整度高
  ：分层干净、工厂/装饰器/仓储等模式用得地道、测试覆盖到位、前后端打通。

  真正的短板集中在**执行安全（无沙箱）**和 **HITL 闭环（revise
  未真正重跑）**两处——如果要继续打磨或在面试中被深挖，这两点是最该优先补的。
