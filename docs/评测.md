  还可以做的优化（按 ROI 排序）

  高优先级：
  1. Prompt cache 优化：Anthropic / OpenAI 都支持。把 system prompt + memory
  注入放在前缀，能命中 90%+ cache 命中率，省 ~50% 成本
  2. Per-state model 选择：PM / Architect 用 Opus/GPT-4，Coder 用 Sonnet，Tester 用
  Haiku → 成本可降 60%
  3. Structured Output 强约束：把 guard 依赖的 JSON 字段用 OpenAI structured output
  / Anthropic tool use 强制，废弃关键词 fallback
  4. 历史压缩策略：到 Tester 阶段，PM 的需求只保留 verdict 那段
  JSON，丢掉自然语言铺垫，能省 30% context

  中优先级：
  5. Speculative decoding / 并行 agent：Architect 和 PM 的部分任务可以并行起来
  6. Memory 检索优化：加 distance 阈值过滤、按 phase 过滤、按当前 state 选不同
  collection
  7. 重试与降级：429/500 退避、长任务断点续跑
  8. Guard 改用 LLM 判定（小模型）：复杂场景下关键词 + JSON 都不准时，用 Haiku
  做判官

  低优先级（但加分）：
  9. Few-shot 示例池：每个 agent 维护若干"高质量历史输出"作为 in-context
  example，按当前任务相似度动态挑选
  10. Tool result caching：同一 query 对 ChromaDB 的检索结果在任务内缓存
  11. Token 预算分配：根据任务复杂度动态调 max_tokens

  SFT 数据构建（针对本项目场景）

  核心思路：把项目的 Trace 直接转成训练数据。这是多 agent 项目相对于单 agent
  项目的天然优势——结构化日志就是数据集。

  数据来源（按质量分层）

                      数量    质量    标注成本
  A. 自然完成的任务   ★★★    中     免费
  B. HITL 审批通过的  ★      高     免费（用户已经评过）
  C. Reviewer APPROVED 自动 ★★★   中     免费
  D. 失败-修订-成功对  ★★    极高   免费（含错误信号）
  E. 人工精修的       ★      最高   贵

  单 agent 维度的 SFT 数据

  每个 agent 单独训练一个专家模型。以 Coder 为例：

  # 一条训练样本
  {
    "messages": [
      {"role": "system",    "content": <coder.md 的内容>},
      {"role": "user",      "content": "做一个论坛后端...[+memory]"},
      {"role": "assistant", "content": "{...PM 输出...}"},
      {"role": "assistant", "content": "{...Architect 输出...}"},
      {"role": "assistant", "content": "<Coder 这次的实际输出>"}      # ← 训练目标
    ],
    "reward": 1.0,        # 用于后续 DPO
    "metadata": {
      "task_id": "...",
      "passed_tests": True,
      "review_verdict": "APPROVED",
      "revision_count": 0
    }
  }

  筛选规则：
  - 只保留 review_verdict == APPROVED && revision_count == 0
  的样本（一次过的最优解）
  - 或保留 revision_count > 0 但最终修订成功的，作为"修复"任务的训练数据

  DPO（偏好学习）数据

  修订循环天然是 DPO 数据生成器：

  {
    "prompt":    <Coder 收到的 messages>,
    "chosen":    <修订后的代码（Tester 通过 + Reviewer APPROVED）>,
    "rejected":  <第一次的代码（Tester 失败）>,
    "metadata": {"failure_reason": "(page-1) 写成了 page"}
  }

  这种数据本项目自动产生——只要把 Trace 里的"失败→成功"对挖出来即可。这是多 agent
  项目的杀手锏数据。

  Agentic RL 数据构建

  Agentic RL（典型代表：Tülu 3 风格、SWE-RL、最近的 RLHF for tool use）和 SFT 不同：
  - SFT 学单步动作：给定上下文，输出这一步该说什么
  - Agentic RL 学整条轨迹：什么时候调工具、调哪个、参数怎么填、错了怎么自救

  针对本项目的设计：

  Episode = 一次完整任务运行
  State   = 当前对话历史 + memory + 工具状态
  Action  = agent 的输出（含工具调用）
  Reward  = 多源信号
     r_terminal      = 最终是否 APPROVED                      (+1)
     r_efficient     = 1 / (revision_count + 1)               (越少修订越好)
     r_test_pass     = 测试通过数 / 总数
     r_tool_success  = 工具调用成功率
     r_cost_penalty  = -α × total_tokens / 10k

  数据规模估算

  要做 SFT，单 agent 大约需要：
  - 冷启动 SFT：1k~10k 高质量样本
  - DPO 偏好对：5k~50k pairs
  - Agentic RL：1k+ 完整轨迹（每条平均 5~7 步）

  本项目要达到这个量级，需要先把任务 throughput 起来——每天跑 100 个真实任务的话，3
  个月攒到 1 万条不难。所以：
  - 短期：先做评测 + harness 优化
  - 中期：搭数据飞轮（每个任务自动入库 + 标注 pipeline）
  - 长期：DPO（最先做，因为修订循环天然有偏好对）→ SFT → Agentic RL

  数据质量保证（容易被问到的细节）

  1. 去重：用 embedding 去重，避免同一类任务样本爆炸
  2. 难度分层：保留各种修订轮数的样本，避免只学"简单一次过"的
  3. 失败案例的价值：保留 ~10% 的失败样本作为 negative，告诉模型"什么不要做"
  4. 数据脱敏：生产数据的 secret/PII 自动扫描清洗
  5. 分布平衡：按 entity 类型、技术栈、任务复杂度分层抽样

  训练后怎么用回项目

  微调后的 5 个小专家模型 ──→ 替换 model_factory 里的对应 client
                         ──→ 同样跑 benchmark 验证
                         ──→ 比较成本/质量曲线

  预期收益（粗估）：
  - Coder 专家模型：成本 -70%（用 8B 替代 Sonnet），一次过率可能从 50% 提到 65%
  - Tester 专家模型：判定准确率 +10%，guard 解析失败率近 0
  - 整体 $/task 可下降 60~80%（生产级跑量才划算）

  ---
  Harness 到底指什么

  Harness = 包在模型外面的所有工程层。从"模型收到 prompt
  前"到"模型输出被消费后"之间的一切基础设施：

  用户输入
     ↓
  ┌─────────────────────────────────────────┐
  │ Harness 层                                │
  │   上下文管理  路由/编排  工具调用          │
  │   检索/记忆   重试/降级  观测/Trace         │
  │   缓存        结构化输出  验证/安全         │
  └─────────────────────────────────────────┘
     ↓
     模型（LLM）
     ↑
  ┌─────────────────────────────────────────┐
  │ Harness 层（输出侧）                      │
  │   解析  验证  路由下一步  写日志            │
  └─────────────────────────────────────────┘
     ↓
  结果

  Harness 不是"单 agent 的专属技术"——它是相对于"模型本体"的概念。单 agent 和多 agent 都有
  harness 层，只是形态不同。

  ---
  单 agent 的 harness vs 多 agent 的 harness

  ---
  为什么会有"多 agent 不好做 harness"的错觉？

  可能来自三个角度的混淆：

  混淆 1：把"harness"等同于"Claude Code / Cursor 那种单 agent 产品的工程层"

  这是特定产品的 harness，不是 harness 概念本身。那些产品解决的是"一个 agent
  怎么用好工具"，多 agent 系统解决的是"一组 agent 怎么协作"——harness 都要做，只是问题不同。

  混淆 2：多 agent 框架（AutoGen / CrewAI）看起来"开箱即用"

  用 AutoGen 确实能几行代码起一个 demo，感觉不用做
  harness——但那是玩具级。本项目就是证据：AutoGen
  给的只是骨架，要做到生产级（可观测、可控、可介入、可记忆、可持久化）必须自己做大量
  harness。

  混淆 3：多 agent 的 harness 有一部分被"编排框架"承担了

  RoundRobin / Selector / 消息路由这些在单 agent 里不存在，在多 agent 里由 AutoGen
  承担。所以直观上感觉 harness 少了——实际上是harness 层更厚了，只是有一层被框架接走了。

  ---
  多 agent harness 工程更难、更多、更有价值

  更难在哪

  1. 状态空间爆炸：单 agent 只有"当前上下文"一个维度，多 agent
  还要管"谁该说话、消息怎么传、何时收束"
  2. 错误传播：一个 agent 输出错了，下游全错；harness 层要做 guard、验证、熔断
  3. Token 分布不均：某个 agent 可能吃掉 70% 预算，harness 要做分桶观测才能发现
  4. 一致性：多个 agent 说的内容要互相对得上——harness 要做消息压缩、幻觉检测
  5. 可观测性更复杂：单 agent 一条时间线，多 agent 是树/图结构

  更多在哪

  除了单 agent 的所有 harness 工作，还要做：
  - Agent 选择策略（LLM selector / FSM / handoff）
  - 状态机熔断（max_rounds / max_revisions）
  - 消息历史裁剪（谁看什么、看多少）
  - Agent 级 cache（system prompt 可独立缓存）
  - 跨 agent 共享状态（memory、工具状态）
  - HITL 的阶段插入点

  更有价值在哪

  这是面试的核心卖点：

  ▎ 多 agent harness 工程的产出物是"可审计的生产流水线"——这是单 agent 再怎么做 harness
  ▎ 都难以达到的。Claude Code 这种单 agent 产品很难做到"给监管/审计看清楚：这段代码是在第 3
  ▎ 轮修订、经过 Reviewer 打了 APPROVED 之后交付的"，因为单 agent
  ▎ 里没有这种显式的阶段边界。多 agent + FSM 的 harness 天然提供了这个能力。

  你的需求是：假设我们把 Memory 模块补强，包括设置相似度阈值、不要固定 2000/800 字符截断、并
  且自建 benchmark 评测集，那么能不能评测这个多 Agent 项目的效果；如果能，应该怎么合理设置这
  些前提，避免拍脑袋。

  答案是：能评测，而且这三件事正好是让评测可信的前提。

  因为当前项目的问题是 Memory 太轻量：固定 Top-K、固定截断、无阈值、无 rerank。这样评测
  Memory 效果时，容易把“噪声上下文”也注入进去，导致结果不稳定。补上阈值、动态切块和 benchmark
  后，就可以做比较严肃的离线评测。

  1. 阈值怎么合理设置

  不要凭感觉设一个固定值。推荐做法：

  先构造一批 query-memory 标注样本：

  query: 当前任务描述
  positive memory: 真正有帮助的历史任务片段
  negative memory: 无关历史片段

  然后跑 ChromaDB 检索，观察相似度/距离分布。

  目标是找到一个阈值，让：

  相关片段尽量保留
  无关片段尽量过滤

  可以用指标调：

  - Precision@K：召回结果里有多少是真的相关。
  - Recall@K：相关历史有没有被找回来。
  - Noise injection rate：注入上下文里无关片段占比。
  - Downstream pass rate：最终任务通过率。

  工程上可以先保守：

  Top-K = 10 粗召回
  相似度低于阈值的丢弃
  最多注入 Top-3

  注意 ChromaDB 返回的可能是 distance，不同 embedding 配置下数值含义不同，所以不能直接说“阈值
  设 0.8”。要基于你自己的 embedding 和数据分布校准。

  面试可以说：

  > 阈值不是手写常数，而是用一小批人工标注的 query-memory 对调出来的。先看相关与不相关样本的
  > 相似度分布，再选一个让 precision 和 recall 平衡的点，最后用 benchmark 验证它对最终任务成
  > 功率是否提升。

  2. 非固定长度存储怎么做

  不要简单 content[:2000]。应该按内容类型动态切块。

  建议：

  - PM 输出：按需求条目、验收标准切。
  - Architect 输出：按模块、接口、技术决策切。
  - Coder 输出：按文件、类、函数切。
  - Tester 输出：按测试用例、失败日志、错误类型切。
  - Reviewer 输出：按 issue、建议项、结论切。

  每个 chunk 不固定字符数，而是设置范围：

  目标：300-800 tokens
  最大：1000 tokens
  太短：合并相邻块
  太长：按语义标题/函数继续拆

  每个 chunk 带 metadata：

  {
    "task_id": "...",
    "agent": "coder",
    "phase": "coding",
    "language": "python",
    "task_type": "bugfix",
    "file": "solution.py",
    "symbol": "is_palindrome",
    "tests_passed": true,
    "approved": true,
    "created_at": "..."
  }

  注入时也不要固定每条 800 字符，而是用 token budget：

  Memory 总预算 = 当前 prompt budget 的 15%-25%
  最多 3-5 个 chunk
  每个 chunk 保留完整语义单元

  面试可以说：

  > 我不会按固定长度截断，因为固定截断可能切断函数或错误日志。更合理的是语义切块 + token
  > budget。存储时保留完整函数、完整 issue、完整测试失败片段；注入时按总 token budget 控制，
  > 而不是每条硬截断。

  3. Benchmark 怎么构建才能评测项目效果

  可以自建一套项目场景 benchmark，而不是只用 HumanEval。

  每个 case 是一个任务包：

  benchmark_case/
    task.yaml
    starter_files/
    hidden_tests/
    expected_behavior.md

  task.yaml 包含：

  id: slugify_to_filename
  type: memory_augmented
  difficulty: easy
  tags: [python, string, reusable_pattern]

  prompt: |
    Implement safe_filename(title: str) -> str.
    It should lowercase, remove punctuation,
    collapse spaces/separators into hyphens.

  expected_files:
    - solution.py

  success:
    hidden_tests_passed: true

  评测维度：

  - hidden tests pass rate
  - 一次通过率
  - 最终通过率
  - revision 次数
  - token 成本
  - 耗时
  - memory 命中率
  - 无关 memory 注入率
  - tool 调用失败率
  - 状态路径是否符合预期

  最关键的是做 ablation：

  A: memory off
  B: memory on, no threshold
  C: memory on, threshold
  D: memory on, threshold + semantic chunking
  E: memory on, threshold + chunking + rerank

  如果 D/E 相比 A/B：

  pass rate 提升
  revision 次数下降
  无关注入率下降
  token 成本可控

  就说明 Memory harness 的优化真的有效。

  4. 能评测哪些效果

  可以评测三类效果。

  第一类：最终任务质量

  hidden tests pass rate
  最终通过率
  代码是否满足接口

  第二类：流程质量

  一次通过率
  平均 revision 次数
  是否卡死
  HITL 触发位置是否合理
  状态机路径是否正确

  第三类：Memory 策略质量

  检索 precision/recall
  相关 chunk 命中率
  无关 chunk 注入率
  memory 注入后 token 增量
  memory 对 pass rate 的提升

  也就是说，能评的不只是“模型生成得好不好”，还包括“harness 策略有没有让 Agent 更稳定”。

  5. 合理设置这些前提的流程

  建议按这个步骤做：

  1. 先建 gold benchmark
     选 30-50 个任务，覆盖 coding、bugfix、refactor、memory reuse、多轮修订。
  2. 给 memory 样本做少量人工标注
     标注哪些历史片段对哪些新任务有帮助。
  3. 调检索阈值
     用标注样本调 Precision@K、Recall@K、Noise Rate。
  4. 调 chunk 策略
     比较固定截断、语义切块、函数级切块在 benchmark 上的差异。
  5. 固定评测配置
     固定模型、temperature、workspace、工具版本、benchmark 版本。
  6. 做 ablation
     每次只改一个变量，比如只加 threshold，不同时改 prompt 和模型。
  7. 记录统计结果
     至少跑多次，避免一次 LLM 随机性误导结论。

  > 可以评测，而且我会把这三件事作为评测可信度的前置条件。当前项目的 Memory 是轻量版，固定
  > Top-K 和固定截断会带来噪声，所以我会先做语义切块、相似度阈值和自建 benchmark。阈值不是拍
  > 脑袋设，而是基于人工标注的 query-memory 样本，观察相关和不相关片段的相似度分布，用
  > Precision@K、Recall@K 和无关注入率来调。存储也不是固定 2000 字符，而是按需求条目、架构模
  > 块、函数、测试失败日志、review issue 做语义切块，并用 token budget 控制注入。最后通过自建
  > benchmark 做 ablation，比如 memory off、memory on、threshold、chunking、rerank 逐步比较，
  > 看 hidden tests pass rate、一次通过率、revision 次数、token 成本和噪声注入率是否改善。这
  > 样才能证明 harness 优化真的提升了 Agent 效果，而不是靠主观感觉。
